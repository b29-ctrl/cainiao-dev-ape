## 〇、一页纸

```
S0      你说需求（有材料先给材料）
S0.1    需求问卷（按品类生成 · 生成前跑冲突校验）
S0.2    需求图（功能地图必出 / 主流程看场景 / 角色图 ≥2 角色必出）
S1      产品功能说明书【v1.0 定稿】 ← 唯一权威，定义"做什么"与验收 V1..Vn
S1.1    任务书（只引用说明书章节 + 本次范围 / 预览环境 / 交付物 / 排期）
S2      UI 效果图
S3      你在调试台里改到点头
S4      冻结（单文件项目：图即码；其他项目：设计令牌 + 截图）
S4.5    接入调度台（项目 + 主理人/大BOSS/AI 成员 + S4 产物交接 + S5 工单草稿）
S5      方案（技术实现由 AI-A 提出）→【门① 方案审】
        → 实施 →【门② 代码审】→ AI-B构建【门③】→ 独立验收【门④】→ 你终验【门⑤】→ tag
```

**一句话分工**：你定**要什么**，AI-C 把它写成**说明书**，AI-A 定**怎么做**，AI-B验**装得上吗**，独立验收人验**真好用吗**。

**三份文本，各有唯一职责（同一件事只写一处）**：

| 写什么 | 唯一出处 | 谁不许写 |
|---|---|---|
| 用户可见行为、业务规则、验收编号 V1..Vn | 《产品功能说明书》 | 任务书、方案 |
| 本次范围、负责人、预览环境、交付物、排期 | 《任务书》 | 说明书 |
| **本项目的任务拆分结果**（阶段→里程碑→小任务、owner、影响清单） | 《任务书·开发计划》 | 说明书、方案 |
| 任务拆分的**规则**（怎么拆、A/B/C 分级、三级基线、写租约） | 《通用流程》§7 / §10 | 说明书、任务书 |
| 技术选型、存储引擎、页面路由、接口、组件结构 | 《方案》 | 说明书 |

## S-1 · 环境初始化（开机第一步，v4.10 新增）

> 装好技能、开新项目，先完成四个前置问题；做完记进 `00_环境.md`，同项目不再问。

### S-1.1 四个前置问题

**① 项目与目录（先于角色）**

先确认目录，再分角色——否则分完才发现 AI 没权限：

| 项 | 要求 |
|---|---|
| 路径 | 盘符级完整路径 |
| 存在 / 可写 | 是否存在、可写 |
| 已有内容 | 有内容要提醒，不得覆盖他人项目 |
| git | 是否 git 仓库、base commit、当前基线 |
| 结构 | 分 `协作\`（任务书/台账/验收证据）与项目源码 |

**② 定 AI 数量 + 每个 AI 的能力（主理人固定 1 个；AI 基准 3 个，可因并行增加）**

先问数量，再问每个 AI 的能力：

- **少于 3 个 AI**：不满足"写码 / 构建 / 审"三角分离，标准流程**不启动**，进入非标准辅助模式（见 S-1.2）；
- **3 个起**：每个 AI 报能力——文件读写 / 浏览器 / 截图 / 构建 / 真机 / git。

> **主理人永远固定 1 个，不拆、不加。** AI 以 3 个为标准配置，因依赖图并行需要可增加席位（5/9），但主理人不变；主理人数永远 ≤ AI 数。

> 只数数量不够：3 个 AI 里若没人会构建，凑够数也分不了 AI-B。

**③ 按能力分配角色（用户只确认，不必自己分）**

AI 根据"数量 + 能力"给出分配方案，用户确认或微调；缺必要能力时，即使数量够也要调整或提示补能力。

| AI 数量 | 推荐分配 |
|---|---|
| **3** | AI-A 写码；AI-B 构建与测试执行；AI-C 审与台账；门④⑤ 由主理人签 |
| **4** | AI-A 拆两个（出方案 + 写码），或留 1 个专做集成 |
| **5** | 条件式：需两路并行 → 2 写码 + 1 集成 + 1 构建 + 1 审计（主理人签门④）；单线程需无人值守验收 → 1 写码 + 1 构建 + 1 独立验收 + 1 审计 + 1 方案/测试支援（主理人签门⑤） |
| **>5** | 按可并行切片、构建槽、验收槽、集成容量算，不按人数机械填满 |

**三条不可破**：

1. 最小四角；多出的 AI 是某角内拆出的**岗位**，不是新角色族；
2. **写码 ≠ 审**，**构建 ≠ 验收**；
3. 门④ 由主理人或指定独立验收人签，自动化只能生成证据、不能自动签。

> AI 的职责是：报出分配方案 + 标出"哪两角必须不同人"，让用户填"哪个 AI 顶哪一角"。用户只做确认，不需要自己设计怎么分。

**④ 选模型【重要，不是平选项】**

> **建议用 PRO 立项，这是流程里唯一一个"强烈建议"的选项。**
>
> 立项前期（S0–S1）要干三件最吃模型能力的事：**搜真实对标产品、复述确认需求、找需求前后矛盾**。
> 普通模型在这三件事上最容易**编造**——而这里编出来的东西会一路传到说明书、方案、代码，**越往后改越贵**。
>
> 所以在勾选器里，PRO 是**放大的主推项**，普通是**降级小项**：
> 选普通会当场出红字警告，且产出必须标 `模型：普通`、对标项一律附链接人工复核。

降级：只有普通模型也能继续流程，但代价是"S0–S1 每一章你都要亲自核一遍"，且门① 会重点查对标真伪。

**门④ 无人值守（一句话）**

> 自动化测试、截图、日志、真机脚本只能生成"门④ 证据 · 待验收"，**不能自动签门④**；未签门④ 不得进门⑤、不得发布。门⑤ 永远由主理人签。

### S-1.2 人手不够 / AI 多，怎么办

**兼多角（AI 少 → 非标准辅助模式）**：少于 3 个 AI 时，允许兼角，但只能分析、起草、做局部改动，**不得签正式门①–⑤、不得宣称标准交付或发布**：

| 可兼 | 不可兼（底线） |
|---|---|
| 一个人兼 AI-A 和AI-B | **AI-A 与 AI-C 不得同一人**（否则自审自写，门①② 作废） |
| 一个人兼 AI-C 和主理人 | **AI-B与独立验收人不得同一人**（否则自建自签，门④ 作废） |

### S-1.2.1 身份冲突熔断（v4.33 新增）

> 之前只写了"不可兼"，但没有**自动判定**。一旦身份冲突，门禁要显式标 `INVALID`，不是靠人自觉。

**规则**：`00_环境.md` 落盘后，AI-C 做一次**身份冲突检查**：

| 冲突 | 判定 |
|---|---|
| 写码者 与 审方案/审代码 同一个人 | 门①、门② 标 `INVALID` |
| 构建者 与 独立验收 同一个人 | 门④ 标 `INVALID` |
| 主理人 兼任 AI-C 的审计席位 | 门①、门② 标 `INVALID` |

**命中任一冲突时**：

1. `00_环境.md` 必须标一行 `门禁状态：INVALID（原因）`；
2. 相关门禁**不得宣称通过**，只能在交付里写"自测，无独立门禁"；
3. 要恢复门禁效力，必须换人后重新核验。

> 这是把"不可兼"从口号变成**可判定的状态**：不是"建议不要"，是"系统判定无效"。

**拆工作（AI 多）**：可以拆，按**子职责**拆，不按文件拆：

| 角色 | 可拆成 |
|---|---|
| AI-A | 出方案的 A + 写码的 B（交接物 = 方案） |
| AI-B | 构建的 A + 真机验收的 B（交接物 = 安装包 + 报告） |
| AI-C | 审方案的 A + 记台账的 B（交接物 = 门禁结论） |

**拆的规矩**：

1. 最小四角不变，拆是"一个角色内分给多人"，不是新增角色；
2. 每拆一个，加一道交接：命名 + 交接物（谁给谁、给什么）；
3. **"做"与"审"永远不得落到同一个人**——拆得再细，这条不动。

> **多个开发 AI 都属于 AI-A 的并行实例，不是新角色**；集成 owner 是本批任务在 AI-A 内部临时指定的职责，也不新增角色。


**主理人拆小组队长（大项目）**：主理人可把"某板块的需求确认权"委托给小组队长，各管一摊、单独推进、最后合并。

但以下三件事**永远只归唯一主理人，不拆**：

1. **门⑤ 终验**；
2. **需求冲突最终裁决**；
3. **发版决定**。

合并防打架两条：**共享契约先冻结**（小组队长不得私改）；**需求冲突只有唯一主理人裁决**。

**授权边界**：小组队长是主理人角色族内的有限授权席位，只在授权板块内确认需求，不得修改跨板块共享契约、不得签门⑤、不得决定发版。授权范围、期限、冲突升级路径和撤回条件必须写入 `00_环境.md`；同一板块的小组队长不得同时担任该板块的 AI-A、AI-B 或 AI-C 签字席位。

**小组队长权限（v4.24）**：只拥有授权板块的需求确认与冲突上报权。可查看指定预览地址和截图，但**不得启动或切换调试台写模式、不得修改源码、不得构建、不得提交、不得签门①–⑤**。需要界面调整时，只提交带页面位置、期望结果和验收条件的 UI 变更请求，由主理人或 AI-C 分类后走对应线路。

边界补充：可确认「需求是否理解正确」，不能确认「代码实现正确」；跨板块可查看、不可修改；无权改变共享契约、公共字段、导航或设计令牌。

## 一、四个角色族 + 独立验收席位（一个都不能少）

| 角色 | 干什么 | 绝对不做 | 每次交付什么 |
|---|---|---|---|
| **主理人** | 定方向、看图拍板、终验、决定发不发版 | 不判断技术方案对错 | 需求原话、批注、验收结论 |
| **AI-A** | 出效果图、出方案、写代码、自测 | 不启动服务器、不跳过评估改码 | 效果图、方案、代码、自测记录 |
| **AI-B** | **构建、打包、签名、部署、装机、运维** | **不改业务代码；不给自己签门④** | 安装包/部署记录、构建日志、失败清单 |
| **AI-C** | 写任务书/变更单、守五道门、审方案与代码、留证据、记台账 | 不写业务代码、不自己发版 | 任务书、门禁结论、台账、证据包 |
| **独立验收人** | 门④ 真机验收并签字（主理人或其书面指定的人，**不得是当次构建参与者**） | 不接受"AI-B说没问题" | 真机验收单（正/负向逐条 + 证据） |

> **通用名 A/B/C**：**AI-A = 写码，AI-B = 构建与测试执行，AI-C = 审与台账**。安装时把你自己的 AI 映射进来（例：你现有的写码 AI → AI-A）。\n> **AI-B 只签门③（构建自检），不签门④**——门④ 必须由主理人或书面指定的独立验收人签，构建者不能自签。
> **门③ 与门④ 必须分开签。** 构建者只能证明"产物生成了"，不能证明"行为正确"。
> AI-B自建自签 = 没有门。这是 v4.2 对 v4.1 的硬修正。

## 二、阶段链（不可跳）

| 阶段 | 谁 | 产出 | 跳过会怎样 |
|---|---|---|---|
| **S0 需求** | 主理人 | 一句话目标 + 硬要求（≤9 条）；有材料先交材料 | 后面全是猜 |
| **S0.1 问卷** | AI-C 生成 / 主理人填 | 问卷答案（**必须先过冲突校验**） | 问出互相矛盾的需求 |
| **S0.2 需求图** | AI-C | 功能地图（必出）· 主流程（有场景时）· 角色权限（≥2 角色必出） | 图上漏一块，方案必漏 |
| **S1 说明书** | AI-C 起草 / 主理人逐章确认 | **《产品功能说明书》v1.0 定稿**，含 V1..Vn | 开发靠猜，做完不对版 |
| **S1.1 任务书** | AI-C | 引用说明书章节 + 本次范围 / 预览环境 / 交付物 / 排期 | 任务书与说明书两份说法 |
| **S2 效果图** | AI-A | **先定 UI 风格**（`UI风格选型.html`）→ 板块 + 子板块 + 用户端 + 管理端，假数据可运行 | 概念错，改到崩溃；风格错，整套返工 |
| **S3 看图批注** | 主理人 | 在调试台里直接改，或逐条「要/不要/挪」 | 需求靠 AI 猜 |
| **S4 冻结** | AI-C | 单文件：图即源码；其他：设计令牌 + 截图 + 基线提交 | 图是图、码是码，白改 |
| **S4.5 接入调度台** | 流程主理人（调度台 DSH） | 调度台项目 + 成员 + 项目目录 + S4 产物交接 + S5 工单草稿 | S4 产物接不进调度台，S5 无输入 |
| **S5 方案** | AI-A | 技术选型 + 六条硬要求 + 逐项落地写法 | 门① 打回 |
| **S6 实施与验收** | AI-A / AI-B / 独立验收人 | 代码 → 构建 → 真机 → 发版 | 上线才炸 |

**阶段必选 ≠ 方式必须一样**：

每个阶段都是必选的，但**用什么工具/方式完成可以选**。例：

| 阶段 | 必选的部分 | 可选的部分 |
|---|---|---|
| S3 看图批注 | 看完图、给出结论 | 在调试台里双击改 / 口头批注 / 逐条「要·不要·挪」 |
| S2 效果图 | 出一份能点的图、覆盖核心板块 | 调试台看 / 浏览器直接开 / 截图给主理人 |
| S4 冻结 | 风格锁定 + 打基线 | 用 git tag / 用归档快照 |

**判断标准**：阶段是「必须发生的事」，工具是「怎么让它发生」——前者不能省，后者可以换。

**四条硬规矩**
1. **说明书不到 `v1.0 已定稿`，不许建方案任务**；S2 效果图可以先做，但它只用于讨论，不能反过来当需求依据。
2. **`v0.x` 推导稿一律不得进入 S5**（详见 17.6）。
3. S2 之前不写码；S4 之前不出方案。
4. 没提交的定稿等于没定。

### 2.1 S1.1 任务书必填：预览与截图环境

| 项 | 必须写清 |
|---|---|
| 服务 owner | 谁负责起/守调试台或开发服务（默认 AI-C） |
| 固定入口 | URL + 端口，例：`http://127.0.0.1:8792/site/index.html` |
| 截图命令 | 一条可直接执行的命令（例：`python 协作\shot.py <url> <宽> <高> <输出>`） |
| 临时文件 | 命名前缀与清理时机 |
| 故障降级 | 入口不可用时怎么办（由 AI-C 书面给出，不由 AI-A 临时决定） |

**规矩**：AI-A 只使用任务书指定入口，**不自行启动服务**；入口不可用时，任务不得进入 S2。

### 2.2 S1.1 任务书必填：任务拆分结果（开发计划）

> 任务拆分结果只写在这里，**不进产品功能说明书**（说明书 §3 只保留"板块→功能"的业务划分）。

| 项 | 必须写清 |
|---|---|
| 阶段 | 阶段 0（骨架/最小契约）→ 板块 1…N → 跨端 → 发布门（见 §7.4） |
| 里程碑 | 每个板块一个可见里程碑（调试台能点、能看、能验） |
| 小任务 | 每阶段拆 N 个，粒度 = 一个可独立验证的变化（§7.4） |
| owner / 集成 owner | 每个任务谁负责；谁负责合入集成分支（§10.1） |
| 排期 | 每阶段 / 每个小任务的预计时长 |
| 批量合并分组 | 用户一次提的一批问题，按 §7.5 分 A/B/C，附六维影响清单 |
| 并行度复核结果 | §7.4.1 算出的 N 与建议 AI 总数；若与 S-1 填的数量不同，写明"接受建议 / 坚持原数及理由" |
| 基线 | 开工前记 `base_commit`，完成后记 `result_commit`；阶段末打 `stage/…` |

**规矩**：没有这份拆分结果，任务书不算写完；说明书里出现"阶段/小任务/owner/分支"字样，视为越界打回。

### 2.3 S2 前置：UI 风格选型（v4.26 新增）

> 风格错了，整套返工。所以出效果图之前，先把风格定死。

**启动方式（自动弹出）**：

```powershell
python "02_工具\启动项目.py" --dir "你的项目目录" --port 8792
```

启动器依次做三件事：

1. 检查项目 `00_环境.md` 里有没有「风格：」；
2. **没有 → 自动弹出 `UI风格选型.html`**（单文件，12 种风格，示例图 CSS 自绘，离线可用）；
3. 起调试台（安全编辑模式）。

**勾选流程**：

1. 在选型页**点卡片**选中（再点一次取消），右上角出现蓝色 ✓，底部显示「已选：X」；
2. 需要深色主题就勾「叠加暗黑模式」；
3. 点 **「确定风格」** → 自动复制成 `风格：7 瑞士极简 Swiss + 暗黑模式`；
4. 把这行粘进 `00_环境.md`（下次启动就不再弹）；
5. AI-A 严格按选定风格出效果图，**不得自行换风格**。

**红线圈**（选型页底部也写了）：

- 一个产品不得混三种风格（主界面扁平、弹窗拟物、活动页孟菲斯 → 用户会觉得不是一个产品）；
- 新拟态不得用于表单、支付、主流程（对比度低，用户点不到）；
- 撞色风格（孟菲斯/Y2K/蒸汽波）只做视觉层与 Banner，正文回中性色；
- 毛玻璃上低端机必须有降级方案。

### 2.3.1 风格的三个阶段：选定 → 可调 → 锁死（v4.30 修正）

> 风格在 **S2 前只是"选个起点"**，真正锁死是在 **S4 冻结**。没看到效果图就锁死，等于盲签。

| 阶段 | 风格状态 | 能做什么 |
|---|---|---|
| **S2 之前** | 选**初始风格**（写进 `00_环境.md`） | 给 AI-A 一个明确起点，避免它自己乱挑 |
| **S2–S3** | **可调** | 看效果图时发现风格不对，可以换（换主风格/调色板/加暗黑），**每换一次重新出图** |
| **S4 冻结** | **锁死** | 写 `风格锁定：是（S4 冻结，日期）`；之后要改 → 变更单 → 重新走 S2–S4 |

**为什么允许 S2–S3 调**：选型页里的缩略图是"风格示意"，不是你产品的样子。只有看到真实效果图，主理人才判断得了风格对不对。**在能看图之前锁死，是拿一张目录页去签合同。**

**为什么要 S4 才锁**：S4 冻结的是"视觉契约"——图即码。冻结之后图不改，码才有唯一依据。冻结前允许试错，冻结后一律走流程。

**锁死之后**：换风格 = 改设计令牌/共享样式/断点 → 本就在 §3.2 的 A 线触发项里，安全编辑会拦住；要改必须出变更单。

**记录格式**（`00_环境.md`）：

```
风格：7 瑞士极简 Swiss + 暗黑        ← S2 前定，S3 可调
风格锁定：否（S3 调整中）
风格锁定：是（S4 冻结，2026-11-08）   ← 冻结后写入
```

### 2.3.2 S4 冻结怎么做（v4.35 新增，一条命令）

**不要手改状态行、不要手打 tag**——用工具：

```bash
python 02_工具/S4_冻结.py --dir "项目目录"
# 可选：--tag s4-freeze-xxx ｜ --dry-run 先看 ｜ --force 重做 ｜ --skip-git 不用 git
```

工具会做四件事：

| 步骤 | 内容 |
|---|---|
| 1 前置检查 | `00_环境.md` 存在、风格已选（**空值/占位符直接拒绝**） |
| 2 改状态 | `风格锁定：否` → `是（S4 冻结，时间，tag 名）` |
| 3 打基线 | `git add -A` → `commit` → `tag`（无 git 时降级为快照） |
| 4 出记录 | 生成 `S4_冻结记录.md`：commit、tag、**每个文件的 SHA256**、冻结后能做/不能做 |

**退出码**：`0` 成功 ｜ `1` 前置不满足 ｜ `2` 已冻结（要 `--force`）

**为什么必须用工具**：冻结是不可逆节点。手改容易漏改、tag 名容易写错、文件清单没人记。工具一次做完并留证据。

### 2.4 S2 效果图分批（v4.31 新增）

> **不是"几个板块出几张图"，是"一份效果图分几批画完"。**

| 项 | 规则 |
|---|---|
| 形态 | **一份效果图**（单个 HTML），内部用左侧导航 / tab 切换多个板块页 |
| 拆分 | 按**批次**拆，不按"一板块一图"拆 |
| 数据 | 假数据，但每个板块页都要能点、能看 |

**分批方式**：

| 批次 | 内容 | 目的 |
|---|---|---|
| **第 1 批** | 骨架（导航 + 布局 + 设计令牌）+ **3 个核心板块** | 定风格与结构，先把最容易翻车的地方验掉 |
| 第 2 批 | 其余板块按同一骨架铺开 | 复用第 1 批的骨架，只填内容 |
| 第 3 批（可选） | 子页面、弹窗、空状态、错误态 | 补齐边角 |

**规矩**：

1. 第 1 批没被主理人点头，**不许开第 2 批**——风格错了后面全返工；
2. 每批都要"能点、能看、能验"，不是静态图；
3. 后续批次**只能复用第 1 批的骨架与令牌**，不得另起一套（否则一个产品长成两个样）。

> 例：校园一卡通 12 板块 → 第 1 批出「总览 + 卡务 + 消费」3 页；点头后再铺门禁、水控、缴费等。

### 2.5 S4.5 接入调度台（v4.46 新增）

> **S4.5 是交接阶段，不是新门禁。** 只负责把 S4 冻结结果交给工单调度台；门①–⑤ 判据不改。

#### 2.5.1 三个命名空间先分开

| 名称 | 定义 |
|---|---|
| 流程主理人 | 仍是唯一协调/决策席位，不得复制成多个 |
| 调度台主理人 | 该唯一席位在调度台中的 DSH/process AI 适配器 |
| 大BOSS | 最终人工拍板席位，不执行 AI 工单，默认不代替独立验收人；单人项目可按单人模式兼门④ |

#### 2.5.2 八步交接

1. 准备 `00_环境.md`、`S4_冻结记录.md`、基线 tag/commit、风格锁定状态。
2. 调度台左侧「＋新建项目」，项目存储位置填真实存在的 S4 目录；目录不存在或不可写时停止并 `@大BOSS`。
3. 双击项目名改成正式项目名。
4. 「AI 成员」加入主理人 DSH、执行 AI（WorkBuddy/CODEX/COZE 等）；大BOSS 以人工席位留在群内，不接收 AI 工单。
5. 在项目群 `@主理人` 发送标准指令。
6. 主理人输出一页 S5 接入摘要；不得直接写码。
7. 新建 `S5 方案评审` 工单，门①，备注写入 `00_环境.md`、S4 冻结记录、tag/commit 完整路径。
8. 派发器到 `待验` 必须停；`@大BOSS` 拍板后才允许进入 S6。演示推进不算真实门禁签收。

#### 2.5.3 标准指令（直接复制）

```text
@主理人 请先读取项目目录下的 S4 冻结产物和 00_环境.md：
1) 确认门禁/签字人/独立验收人；
2) 确认 AI 席位与角色映射；
3) 确认自动流转边界（重试/超时/预算/熔断/急停）；
4) 输出一页 S5 接入摘要，不要直接开始写码；等我确认后再建 S5 工单。
```

主理人必须把 S4 项目目录作为 cwd。文件不存在、路径不可读、冻结记录与 tag/commit 不一致时，停止并 `@大BOSS`，不得猜测或自行补造。

#### 2.5.4 急停口径

- 调度台提供「暂停 / 继续 / 停止 / 急停」。
- 急停会终止派发器、把进行中工单转失败，并通知大BOSS。
- 发现死循环时，先点急停，再等大BOSS/主理人判断；不得手工改台账掩盖状态。
- 门①、门④等门禁停点必须 `@大BOSS`，派发器不得自动越过。
- 重试上限、超时、无进展和熔断的执行规则引用调度台任务书；技能包只规定必须在 S4 冻结前写清策略。

#### 2.5.5 席位映射

| 技能包角色 | 调度台席位 | 是否 AI | 权限 |
|---|---|---|---|
| 主理人 | DSH 适配器（process） | AI | 方案/主控/交接；不签门④/⑤ |
| 大BOSS | `boss` 人工席位（type=human） | 人 | 拍板、暂停/继续/停止/急停；不执行 AI 工单 |
| AI-A 写码 | CODEX/DSH 适配器 | AI | 只做指派范围 |
| AI-B 构建/真机 | WorkBuddy 适配器 | AI | 提供门③证据 |
| AI-C 审计/台账 | COZE/DSH 适配器 | AI | 门①② |
| 独立验收 | 人工席位（不得是构建者） | 人 | 门④ |
| 小组队长 | 调度台项目成员/只读或指定范围席位 | 人 | 仅授权板块需求确认，不写码、不签门①–⑤ |

**硬规则**：

1. 大BOSS 不是 AI，不得把工单派给 `boss`。
2. 独立验收人不得是写码者/构建者；有第二真人时优先第二真人。**单人项目**允许大BOSS本人兼门④，前提是非写码/构建者，且门④、门⑤分两次签并记录“单人模式”。主理人（DSH AI）不得兼门④。
3. 写码者不得审门②；构建者不得签门④；门⑤由大BOSS终验。
4. 主理人只有 1 个，AI 可以有多席；大BOSS 不占 AI 数量。
5. 门④缺失合格独立验收人时，门④标记为无效，不得宣称标准流程通过。

#### 2.5.6 没有调度台：S4.5-Lite（降级，不阻断流程）

> 调度台是**可选加速器**，不是流程必需品。别人没有调度台时，S4.5 不能照抄“建调度台项目”，改走 S4.5-Lite；门①–⑤ 仍必须人工签。

| 项目 | 有调度台（S4.5） | 没调度台（S4.5-Lite） |
|---|---|---|
| 项目载体 | 调度台项目 + 项目群 | 项目目录 `协作/S4_接入卡.md` |
| 派单 | 派发器按工单派给 AI | 人工把任务书/接入卡发给 AI |
| 状态跟踪 | 调度台台账 + 项目群摘要 | 共享表格 / 任务书 / 协作目录 |
| 暂停/急停 | 项目按钮 | 人工通知所有 AI 停止 + 记录 |
| 大BOSS 提醒 | 群内 `@大BOSS` | 人工通知大BOSS并记录 |
| 门禁 | 派发器停在待验，人工签 | 人工到点停下并签，证据入 `协作/验收` |

**S4.5-Lite 六步**：

1. 照常完成 S4 冻结（tag/commit + `S4_冻结记录.md`）。
2. 复制 `03_模板/S4_接入卡.md` 到项目 `协作/S4_接入卡.md`，填项目目录、S4 产物、AI 席位、大BOSS、门禁停点、自动流转边界。
3. 在接入卡里写清 S5 范围，以及“谁把哪份任务发给哪个 AI”。
4. 人工派 S5：把接入卡 + `00_环境.md` + S4 冻结记录发给主理人/AI-A，停在门①。
5. 门①由大BOSS拍板并留证；S6 继续人工派单，门②③④⑤ 人工签。
6. 以后接入调度台时，用这张接入卡创建项目、导入成员和路径，不需要重做 S4。

硬规则：

- 没有调度台就**不要写“已自动派单/已自动回件”**，状态以人工记录为准；
- S4.5-Lite 不新增门禁，也不能降低门①–⑤ 的判据；
- 多项目/多工单时必须有共享台账，否则视为流程不合格。

| 项目 | 至少写清 |

## 三、两条线 + 一条快捷单（v4.2 新增，严重项 5）

| 类型 | 走哪条 | 起点 |
|---|---|---|
| 改功能、改逻辑、改数据、修 BUG | **A 线（需求型）** | 口述 → AI-C 写任务书 |
| 改界面、改样式、改布局、改文案 | **B 线（UI 型）** | 调试台里改 → 定稿 → AI-C 出变更单 |
| **L0/L1 微改**（见 3.1） | **快捷单** | 变更单 → 改 → 截图 → AI-C 复核 → 主理人确认 |

### 3.1 快捷单适用条件（三条同时满足）

1. **只动 L0 文案 / L1 样式**（颜色、字号、间距、圆角、图标）；
2. **不触**共享组件、设计令牌、数据结构、接口、依赖、构建与发布配置；
3. **不改**断点与布局骨架。

**快捷单流程**：变更单（可一句话）→ 备份 → 修改 → 桌面/手机各一张截图 → AI-C 复核（门②与门③合并成一次）→ 主理人确认 → 提交。
**门④ 仅在布局/断点受影响时执行**；否则免。

**不满足任一条 → 回完整五门，不许"先做后补"。**

**B 线可改范围以 §3.2 的「纯 B 线」清单为准，越界即走 A 线。**

### 3.2 编辑权限与越界处理（v4.24 新增）

> A/B 分类以 diff 的影响域为准，不以「看起来像 UI」判断。

**主理人调试台默认开启 UI 安全编辑模式**：只允许 L0 文案和 L1 局部样式保存。diff 命中脚本、数据、事件、DOM 增删、共享组件、设计令牌、断点或布局骨架时，保存操作转为候选补丁，不做正式落盘；由 AI-C 分类决定走 B 线快捷单或 A 线任务书。**门②审 diff 只作最后防线，不替代编辑时的保护。**

三层防护（缺一不可，但不新增门禁）：

| 层 | 措施 |
|---|---|
| 操作层 | 主理人编辑期间独占写租约；AI-A 不编辑同一文件；开工前记 base_commit，结束生成完整 diff |
| 技术层 | 调试台 UI 安全编辑模式：只允许文本节点和局部样式；触碰 `<script>`、`data-*`、存储键、事件、DOM 结构、共享样式时阻止保存或转变更请求 |
| 门禁层 | AI-C 构建前先审 diff；越界立即转 A 线任务书，不得直接交 AI-B 构建或提交 |

**A 线触发项**（触及任一即走 A 线）：

| 类别 | A 线触发项 |
|---|---|
| 页面结构 | 增删移动 DOM、改区块层级、改 class 语义、改 id、改表单字段结构 |
| 共享 UI | 共享组件、全局样式、设计令牌、通用布局容器 |
| 响应式 | 断点值、断点归属、布局骨架、容器查询 |
| 数据 | 数据结构、字段、schema、存储键、迁移、导入导出格式 |
| 接口 | API、请求/响应字段、事件名、权限边界 |
| 状态逻辑 | store/state 形状、计算规则、校验规则、业务状态 |
| 依赖与构建 | 依赖、版本、构建配置、环境变量、资源来源 |
| 安全 | 鉴权、密钥引用、CSP、跨域和敏感数据处理 |

**纯 B 线只允许**：已有节点的文案；不改变结构的局部颜色、字号、间距、圆角；不碰共享变量和断点的局部视觉调整。

**拿不准时**：不直接保存，标记「待分类」交 AI-C 判定；未分类期间禁止 AI-B 构建和提交。

## 四、五道门（判据必须可量化）

| 门 | 谁签 | 判据 | 不通过 |
|---|---|---|---|
| **① 方案审** | AI-C | 能落地（文件+行号+可粘贴）/ 影响面说清 / 不冲突 / 回滚点齐 | 打回重写，不"边改边谈" |
| **② 代码审** | AI-C | **只读不跑**：参数没写反、边界没漏、没误改别处 | 打回 |
| **③ 构建自检** | **AI-B** | 编译/打包成功、产物版本号对、静态检查零错误、**检查命令与退出码入档** | 退回 AI-A |
| **④ 独立验收** | **独立验收人**（非构建参与者） | 正向 N 项 + **负向 3 项** + 证据；AI-B只交包/日志/截图/失败清单 | 退回 |
| **⑤ 终验发版** | 主理人 | 只认证据矩阵，缺任一 V 项不得签 | 不发版 |

### 4.1 门禁证据矩阵（v4.2 新增，严重项 4）

**《产品功能说明书》里每个验收项必须编号 `V1…Vn`；任务书只引用编号，不新增、不改写。** 交付包必须逐行对应，缺一行 = 该项未验：

| 编号 | 测试输入 / 操作 | 期望结果 | 实际结果 | 命令或复现步骤 | 证据（路径 + hash） |
|---|---|---|---|---|---|
| V1 | 手机 390 打开首页 | 无横向滚动 | — | 截图 + `scrollWidth` 读数 | `协作\验收\…png` `a1b2…` |
| V2 | … | … | … | … | … |

- **门③** 必须给"检查/测试命令 + 退出码"；无测试框架的项目用静态检查脚本代替，不许空着。
- **门⑤** 缺任一 V 项**不得签字**；hash 只能证明"文件没变"，不能证明"功能正确"。

### 4.1.0 矩阵别手写，用工具生成（v4.36 新增）

```bash
python 02_工具/门禁矩阵.py --doc "S1_产品功能说明书_v1.0.md" --task "S1.1_任务书.md"
```

| 它做什么 | 输出 |
|---|---|
| 从说明书验收章节自动抽 `V-*` / `N*` 项 | 空矩阵（状态列待填） |
| 从任务书抽功能 ID，与验收项比对 | **漏交付清单**（任务书要求了但验收没覆盖） |
| 附验收纪律三条 + 正向/负向计数 | 直接进交付包 |

**退出码**：`0` 无漏交付 ｜ `1` 找不到验收项 ｜ `2` **有漏交付**（矩阵仍生成）

> 漏交付是门禁最常见的漏网之鱼：任务书写了"分页"，验收却没测分页。工具会把"任务书有、验收没有"的项直接列出来。

### 4.1.1 验收纪律三条（v4.33 新增）

> 一卡通真跑暴露的三个坑，写死在这里：

**① 范围一致**：任务书里要求的每一项（页面、交互、分页、导出…），验收必须逐条覆盖。任务书写了"分页"，验收却没测分页 → 就是**漏交付**，不得通过。

**② 测试结论不越界**：`10/10 单测通过` 只能证明"这 10 条逻辑对"，**不能**代表"页面功能可跑"。自测、单测、UI 手测三者结论分开写，谁测的、测的什么，不能混。

**③ 原型不虚假承诺**：未实现的能力**不得**写进 UI 文案或验收。原型只改了本地状态（卡状态字段），就不能在按钮/提示里写"挂失后消费与门禁立即拦截"——那是把没做的功能说成做了。

**证据矩阵补一列「状态」**：

| 状态 | 含义 |
|---|---|
| 通过 | 有证据、有实际结果 |
| **未覆盖** | 任务书要求了，但没做/没测（必须写原因，不得算通过） |
| 阻断 | 做了但失败 |

### 7.1 单号规则

```

### 7.2 骨架单必须冻结的共享契约（v4.2 新增，严重项 6）

| 冻结项 | 例子 |
|---|---|

1. 一句话目标（做完能干什么）
2. 板块 + 子板块（**名词必须与效果图一致**）

5. 验收：正向 + 负向 3 条
6. 交回证据：diff --stat / hash / 截图 / 实测数字

### 7.4 阶段、里程碑与任务粒度（v4.12 新增）

**板块是里程碑，不等于阶段。** 阶段除了板块，还要装门控与跨端工作：

| 阶段 | 内容 | 计入"板块数" |
|---|---|---|
| 阶段 0 | 骨架、最小共享契约（路由/状态/API 签名）、迁移骨架、测试桩 | 否 |
| 板块阶段 1…N | 按依赖与优先级逐块交付，每块一个可见里程碑 | 是 |
| 跨端阶段 | 发版、性能、兼容、部署 | 否 |
| 发布门 | 独立验收、终验、tag | 否 |

**数据层不能作为完整横向阶段先做完**，分两类：

- **项目级最小契约**（存储接口、迁移框架、权限边界）→ 放阶段 0；
- **板块业务数据**（表、接口、状态、迁移）→ 随该板块竖向切片一起交付，**禁止在阶段 0 一次性铺完整数据层**（超前猜字段必返工）。

**小任务粒度**：

- 一个可独立验证的**用户可见变化**，或一个可独立验证的**系统能力**；
- 后端、迁移、安全、构建等用户不可见的任务，必须用**可观察断言**验收，不得因此与多个逻辑改动合并；
- 实现过程中允许本地小提交；**合入主线时每个小任务必须形成一个明确可回滚的合并点**；
- 单个板块超过工期时，按"显示 → 交互 → 持久化"连续拆成子里程碑，但仍只算同一板块阶段。

### 7.4.1 并行度复核：AI 数量建议（v4.19 修订）

S-1 填写的 AI 数量是初值。并行度分**两次**复核：

1. **S0.2** 需求图定稿后，从业务依赖给出"初版可并行切片数"和人数建议；
2. **S1.1 / S5** 任务拆分及方案确定共享文件、接口、数据迁移和构建资源后，**冻结本次并行度**。

设：

- `N` = 经依赖图和资源条件确认后，可同时进行的独立写码切片数；
- `I` = 1（N > 1 时必须有独立集成席位），否则为 0；
- `B` = 构建席位，默认 1；
- `C` = 审计席位，默认 1；
- `V` = 主理人不能签门④ 且已指定独立 AI 验收席位时为 1，否则为 0。

**建议 AI 总数 = N + I + B + C + V。**

并行写码 AI 数仍受 §10.1.1 的安全线和停止条件约束，**不得因为 AI 数量足够就超过上限**。

总 AI 数高于建议值**不强制裁撤**；多出的 AI 只能转做独立测试、审查、文档或待命，**不得增加同批未合并写码分支**。

出现范围变更、共享契约变更、数据迁移新增或 §10.1.1 停止线触发时，必须重新计算 N 并更新任务书开发计划。

**两张依赖图，N 取较小值**：

| 层级 | 时点 | 能判断什么 |
|---|---|---|
| 业务依赖图 | S0.2 | 哪些功能模块可独立推进 |
| 实现依赖图 | S1.1 / S5 | 哪些文件、组件、接口、数据和构建资源可真正并行 |

> 例：进销存业务上 3 路可并行，但需另配 1 个集成席位 → 建议 3(写码) + 1(集成) + 1(构建) + 1(审) = **6 个 AI**；同时受"未合并分支 ≤2"安全线约束，实际活动写码分支最多 2 路。

### 7.5 批量问题合并规则（v4.12 新增）

用户一次提多个问题，AI 先交**影响清单**，再分级，不得靠自觉：

| 维度 | 要列的证据 |

| 接口 | API、事件、消息、权限边界 |
| 消费者 | 搜索到的引用文件/模块 |
| 验证 | 受影响 V 项、回归范围 |

| 级 | 判定 | 处理 |
|---|---|---|
| **A 可合并** | 影响域完全不相交，不触共享组件、契约、数据、依赖、构建 | 一次处理 |
| **B 谨慎合并** | 同属一个用户能力，影响域相交但无公共契约变化 | 合并，逐条独立验收 |
| **C 必须拆分** | 触及共享契约、schema/迁移、授权、接口、依赖、构建、发布，或任一项失败会阻塞其他项验收 | 逐个任务、逐个过门禁 |

**两条硬约束**：

1. 分组前必须提交影响清单与消费者清单，**缺失即不能合并**；
2. "同一板块"不能单独作为可合并证据——同板块里的共享表格样式仍可能影响全站。

### 7.6 任务书别手写，用工具生成骨架（v4.37 新增）

```bash

```

## 十、回滚与版本

| 层 | 手段 | 何时用 |
|---|---|---|
| 单次改动 | 调试台「撤销」/ IDE 本地历史 | 刚改完就不对 |
| 文件级 | `.history\` 30 份 / 编辑器本地历史 | 撤销退太多了 |
| 项目级 | **git 提交** | 每次定稿一次，hash 就是回滚点 |
| 发布级 | tag + 版本号 + 归档产物 | 发版时 |

**发布三件套（缺一不算发布）**：唯一版本号 + 按版本归档的产物（含 mapping/符号表）+ 源码已提交并打 tag。

**提交纪律**：`git add <指定文件>`，**禁止 `-A`**——会把别人的手改卷进错误提交。

### 10.1 并行开发与基线同步（v4.12 新增）

**基线分三级，不要求每个微任务都打 tag：**

| 对象 | 标识 | 用途 |
|---|---|---|
| 小任务 | commit hash（台账记 `base_commit` + `result_commit`） | 精确回滚 |
| 阶段冻结 | `stage/s6-stock-03` | 多 AI 集成与验收 |
| 正式发布 | `vX.Y.Z` | 发布归档 |

**命名**：任务台账 ID `S6-STOCK-03`；工作分支 `slice/s6-stock-03`；阶段基线 `stage/s6-stock-03`；**禁止把任务 ID 直接当发布 tag**。

**并行写租约**（分文件不够，还要租约）：

- 同一文件、同一目录、同一共享组件或同一契约只能有一个 owner；
- 并行前建立写租约：owner、文件范围、涉及接口/数据、起始 commit、释放时间；
- 跨文件共享语义仍须登记消费者。

**合并顺序**：

- 不存在"先提交者自动占基线"；
- 每 AI 使用独立分支/独立 worktree，开工前登记 base commit；
- 由集成 owner 合入集成分支，记录新 integration_commit；
- **共享分支禁止 rebase**，只有未共享的本地分支可 rebase；
- 合并后必须重跑受影响门禁。

**无共享 git 仓库时**：只能串行；AI 不能操作 git 时，只提交补丁 + 受影响文件清单，由集成 owner 应用——不得让两个 AI 直接写同一工作区。

**C 级子任务以"单一回滚单元"为约束**：最多包含一个共享契约变更或一个 schema 迁移；源文件数、净增删行数、迁移数、依赖数按项目 11 格设预算；超预算视为拆单失败，需 AI-A 与 AI-C 共同批准原子例外并补回归计划。文件少但风险高也应拆（例：10 行权限判断、一个不可逆迁移）。

---

### 10.1.1 并行准入与人数上限（v4.14 新增）

并行开发只在同时满足以下条件时启用：

1. 依赖图与写租约清楚，当前切片文件、共享组件和契约互不相交；
2. 有共享 git 仓库；每个开发 AI 使用独立分支和独立 worktree，且开工时登记 base_commit；
3. 已指定本批任务的集成 owner；多分支批次中，集成 owner 由 AI-A 担任，不承担同一批功能切片；
4. 构建、测试、端口、数据库或测试数据、签名和产物目录相互隔离；共享资源不可隔离时串行。

**并行开发 AI 数 = min（独立可写切片数，开发 AI 数，可并行构建/验收容量）；存在多个未合并分支时，至少留 1 名 AI-A 专做集成。**

分支合并前只做开发自检；**门③统一签在集成分支的 integration_commit，门④统一签在里程碑最终集成候选**，不按开发分支重复签。

出现以下任一情况，暂停派新任务，先排空合并队列：

- 未合并的编码分支超过 2 个；
- 合并队列超过 1 个；
- 两个分支修改同一共享文件、组件或契约；
- 集成分支任一门禁未通过；
- 集成 owner 无法持续处理合并。

**停止动作固定为**：暂停新任务 → 处理合并队列 → 跑受影响门禁 → 重新确认可并行切片 → 再恢复派工。

**没有共享 git、独立 worktree 或独立验证资源时，不允许并行；AI 再多也只按串行队列分配。**

---

### 10.1.2 共享契约、迁移与敏感资源租约（v4.20 新增）

1. 共享契约、API 签名、数据库 schema 各只有一个 active owner；同一 contract_id 未合入前，其他分支不得修改。
2. 删除或移动文件前必须核对 active 租约与消费者；命中即拒绝合并。
3. schema migration **串行**生成和合入；每次同时验证空库初始化和旧数据升级。
4. 正式门③只签集成分支，必须跑受影响测试、契约测试和集成冒烟；分支自检不能代替。
5. 共享分支和发布 tag 禁止 force push、删除、rebase、reset 后强推；合并前后记录 base/integration commit。
6. 生产密钥不进入分支/worktree；测试凭据和测试数据按分支隔离；无沙箱的第三方接口禁止并行。
7. 共享端口、模拟器、硬件、签名目录和测试库必须登记独占时间槽；不能隔离即串行。

**租约登记**：AI-C 在开发计划登记 `contract_id、owner、消费者、base_commit、状态`；同一 contract_id 同一时刻只有一个 active 租约。合入前核对 git diff，越界即拒绝合并。

**租约登记人**：AI-C 拆成审计席 C1 与台账席 C2 时，租约审核、冲突判定、批准与释放归 C1；C2 只记录状态与证据，不得代替 C1 批准或释放租约。

**租约生命周期**：`active → released / cancelled / expired`；过期或 owner 离线时由 AI-C 重新核准，不得静默转给另一 AI。

**发布 tag 校验**：只有门⑤通过后由主理人创建；必须匹配 `vX.Y.Z`、指向最终 integration commit，并与页脚/README/CHANGELOG 版本一致；已发布 tag 禁止移动或删除。

**分支保护**：共享分支必须启用禁止 force push、禁止删除和禁止改写历史——这是仓库配置，不只写在流程文字里。

**租约释放条件**：只有 result_commit 已合入或任务取消时，AI-C 才能把租约改为 released/cancelled；expired 必须重新核准。

**分支保护核验**：`00_环境.md` 必须记录共享分支已开启禁 force push、禁删除、禁改写历史，并由 AI-C 在首次并行前核验。

## 十二、被拦了怎么办（v4.2 分类，严重项 9）

**先分清是哪一类，两类处置完全不同：**

| 类型 | 例子 | 处置 |
|---|---|---|
| **能力 / 兼容失败** | 脚本执行器不可用、浏览器缺失、路径格式不兼容、端口冲突 | 可按序降级：换执行体 → 换输入 → 换证据 → 才上报 |
| **权限 / 安全策略 / 审批拒绝** | 文件写入被拒、网络访问被禁、命令被策略拦截、审批未通过 | **禁止更换执行体绕过**；立即停止，上报原命令 + 目的 + **三个合规备选** |

**一句话**：换工具解决"不会"，不解决"不让"。把"不让"当"不会"处理，就是绕过边界。

## 十六、需求问卷生成法（S0.1，v4.4 新增）

> 需求不能靠"你想做什么"问出来，要靠"同行已经有什么"反推出来。
> 一份固定的通用问卷不够用：进销存该问多仓、批次，课程表该问单双周、节次——题目必须**按品类生成**。

### 16.1 五步生成

| 步 | 做什么 | 产出 |
|---|---|---|
| 1 定品类词 | 用行业通用词（进销存 / 排课 / 会员 / 工单 / 记账），不用自己的叫法 | 一个词 |
| 2 找对标 | 搜"<品类> 功能模块"或"核心功能拆解"，取 2–3 家头部产品的**官方功能页** | 3–6 个对象 |
| 3 抄模块 | 把它们的模块名原样抄成一张清单 | 板块候选表 |
| 4 判取舍 | 每项标 **必做 / 二期 / 不做**，并写"不做"的理由 | 功能矩阵 |
| 5 反推题目 | 必做项→功能勾选；二期项→风险开关；不做项→反向题 | 问卷 |

### 16.1.1 对标红线：只认真实存在的产品（v4.9 新增）

> **对标的目的不是让 AI 显得博学，是让问卷有据可查。拿不出链接的"对标"就是虚构，直接打回。**

| # | 硬要求 |
|---|---|
| 1 | 每个对标对象必须给出**可点击链接**：官网 / 应用商店 / GitHub / 官方文档。只给名字不给链接 = 不合格 |
| 2 | 每条功能点必须能指出它出自**哪个产品的哪一块**（例：`多仓库 ← 管家婆进销存「库存管理」`），不能只写"参考某类产品" |
| 3 | 取证口径：链接 + 抓取时间 + 关键证据（页面摘要、GitHub 星数/许可证等字段） |
| 4 | **闭源产品**（管家婆、金蝶、超级课程表等）只参考**公开的功能清单**，并标注"闭源，实现未验证" |
| 5 | **禁止**：编造产品名、编造功能、编造"业内都这样"、引用不存在的仓库、虚构星数/许可证 |
| 6 | 搜不到真实对标时，明确写"未找到公开对标"，改用行业常识并**标注为 AI 建议**——不许拿常识冒充对标 |

**判据**：任何一个对标对象，点开链接能在 3 分钟内看到和问卷功能对应的内容，才算真对标。


### 16.2 三层结构（顺序不能反）

```
第 1 步  选板块 → 展开 → 勾功能     （先定骨架，再定细节）
第 2 步  会翻倍工期的取舍            （每个都带"不问会怎样"）
第 3 步  明确不做（反向题）          （选中的是"不要"）
```

**为什么必须先板块后功能**：一上来铺 40 道题，用户思路会乱；先给 8–9 个板块，勾谁看谁。

### 16.3 三级 AI 兜底（只产生"候选"，不产生结论）

| 级别 | 位置 | 作用 |
|---|---|---|
| 全局 | 第 1 步最上 | "这些板块我都不懂，全部按常规给我一套" |
| 板块 | 每个板块展开后第一行 | "这个板块我不太懂，按常规给我勾" |
| 兜底 | 每个板块末尾 + 板块列表末尾 | "其他功能"、"其他板块" |

**三条铁规**：

1. **AI 兜底勾出的每一项都是「候选」**，必须由用户在"生成答案"前确认；未确认的候选不得进入答案。
2. **默认配置是拿来删的，不是拿来交的**；取消勾选不清空用户已选。
3. **答案里每项必须标来源**：`材料 / AI 建议 / 主理人确认`，以及状态：`必做 / 二期 / 不做 / 待确认`。

> 冲突校验见 16.10——同一个能力不许同时出现在"要"和"不要"里。

### 16.4 题型视觉语义（统一，不许混用）

| 题型 | 视觉 | 含义 |
|---|---|---|
| 普通选择 | 白底 | 选中的就是要的 |
| **风险开关** | **红色左条** | 选"要"会让工期或成本翻倍 |
| **反向题** | **深灰左条 + 黑底标签 + 大字** | 选中的是**不要**的 |
| AI 建议 | 蓝色信息条 | 我的推荐，不是你的决定 |

### 16.5 两条硬规矩

1. **每题必须带"不问会怎样"**——说不出后果的问题，就是没想清楚该不该问。
2. **没有默认值时也要给建议**——例如"这四项先都别勾"，沉默不等于推荐。

### 16.6 交付形态

可勾选的单页 HTML（零依赖、双击即用），底部"生成答案"输出分组文本，粘回对话即可。
不给 Word/PDF 填空表：勾选比打字快，且能自动分组。

### 16.7 品类 → 板块对照（示例，非穷举）

| 品类 | 典型板块 |
|---|---|
| 进销存 | 商品档案 / 采购 / 销售 / 库存 / 往来资金 / 报表 / 单据打印 / 权限日志 / 基础设置 |
| 课程表 | 课表 / 节次与学期 / 天气 / 图片识别 / 摘要 / 提醒 / 数据 / 设置 |
| 会员 | 会员档案 / 储值 / 次数卡 / 消费记录 / 营销 / 报表 |
| 排课 | 班级 / 教师 / 教室 / 课程 / 调课代课 / 统计 |
| 工单 | 报单 / 派单 / 处理 / 回访 / 知识库 / 统计 |

### 16.8 材料优先：先收，再问（v4.4 补）

**用户手上可能已经有明确需求**（写好的文档、截图、竞品链接、产品说明）。这时候直接甩问卷，等于让他把说过的话再说一遍。

#### 顺序

```
先问一句：你手上有没有已经想好的需求？
 ├─ 没有 → 直接出全量问卷（16.1–16.7）
 └─ 有   → ① 收材料（文字 / 文档 / 图片 / 链接）
           ② 我先复述一遍"我读到了什么"（结构化清单），你确认
           ③ 再出"定向问卷"：只问没写到的、写模糊的、有风险的
           ④ 材料里明确的"不要"，直接预勾进反向题，你确认即可
```

#### 三条规矩

1. **先复述，再提问**：读完材料先给一张"我理解的需求清单"，让用户纠错；不复述就直接出题，会把误读带进方案。
2. **每项标来源**：预填项必须标明 `来自你的材料` / `AI 按行业默认` / `你这次选的`。后期吵架时，这是唯一能说清依据的东西。
3. **矛盾要单独列**：材料里前后冲突（例：一处写"只有自己用"，另一处写"发给同学"），不要替用户拍板，单列一张「待你确认的矛盾点」。

#### 材料多少的处理

| 材料情况 | 怎么处理 |
|---|---|
| 一句话需求 | 直接出问卷 |
| 一页文档 / 几张截图 | 先出需求摘要卡（半页），再出定向问卷 |
| 长文档（>10 页） | 先出「摘要卡 + 冲突清单」，确认后再出问卷 |
| 只有图片（手写、竞品截图） | 先识别成文字（离线 OCR），复述后出问卷 |

#### 隐私红线

材料里可能有学生名单、客户资料、工资表 → **只在本机处理，不外传、不入库、不写进单据**；截图里的手机号、身份证号要打码后再引用。

### 16.9 需求可视化：三种视图 + 两种交付格式

**先分清两件不同的事**——以前这里混在一起了。

#### 16.9.1 视图类型（画什么内容）

| 视图 | 回答什么 | 什么时候必须出 |
|---|---|---|
| **功能地图** | 到底要做什么 | **每次必出** |
| **主流程** | 用户每天怎么用它 | 有明确使用场景时必出 |
| **角色权限图** | 谁能看、谁能改 | **出现 2 个及以上角色时必出**（不许只把角色塞进流程节点） |

#### 16.9.2 交付格式（怎么看）

| 格式 | 用途 |
|---|---|
| 静态 PNG（1600 宽） | 发微信、打印、贴文档 |
| 无限画布 HTML | 自己推敲、评审会放大看细节（拖拽 / 滚轮 / 双击定位 / `0` 回全局） |

**格式不是第三种图。** 一份内容可以用两种格式交付，但视图类型不能省。

#### 16.9.3 一致性（新增，防自相矛盾）

同一功能在**功能地图 / 流程图 / 产品功能说明书**里的"做 / 不做"必须一致：

- 功能地图上标"明确不要"的项，说明书里不得出现在"必做功能"；
- 流程图里画了"采购退货"，功能地图就不能标"不要"；
- 发现冲突 → **禁止定稿**，先回去问主理人。

**画布只做浏览，不做批注**（试过便签，四步才能说一句话，不如直接说）。

### 16.10 冲突校验（生成答案之前的硬闸门）

**同一能力不许同时出现在"要 / 风险选择 / 明确不要"三处。**

| 冲突类型 | 例子 | 处理 |
|---|---|---|
| 要 × 不要 | 勾了「毛利表」，又勾「不算利润，只看流水」 | 阻断，要求二选一 |
| 要 × 风险选择 | 勾了「应收应付」，风险题选「全部现结」 | 阻断，说明两者互斥 |
| 常规集 × 反向题 | AI 常规集勾了「库存预警」，反向题又砍掉 | 以反向题为准，但要提示"AI 建议已作废" |
| 单选互斥 | 学制选了"只做大学"又勾"单双周"（大学也可以没有） | 降为提示，不阻断 |

**执行方式**：点「生成答案」时先跑校验；有阻断冲突则**不生成、不复制**，逐条列出"第 X 题 与 第 Y 题 冲突"，让用户选一个。

### 16.11 唯一 ID 与来源（贯穿问卷 → 图 → 说明书 → 验收）

| 层 | ID 规则 | 例子 |
|---|---|---|
| 功能 | `B-{品类}-{板块}-{序号}` | `B-INV-STOCK-03` |
| 验收 | `V-{功能 ID}` 或 `V{n}` | `V-B-INV-STOCK-03` |
| 图 | 卡片上标同一 ID（小字即可） | 库存卡右上角 `B-INV-STOCK-03` |

**用途**：
- 图上改一项，能立刻定位到说明书哪一节、哪个验收项；
- 出争议时，"这条需求哪来的"有唯一答案。

**来源标记**（每项必带）：

| 标记 | 含义 |
|---|---|
| `材料` | 来自主理人给的文档/截图 |
| `AI建议` | 行业常规，尚未确认 |
| `主理人确认` | 明确点过头 |
| `待确认` | 还没定，**不得进 v1.0 说明书的必做功能** |

### 16.12 机器可读的问题模型（v4.7 新增）

> 光有"视觉结构"造不出合规问卷。每题、每个选项都必须落到字段上，否则校验无从谈起。

**问卷的真相是一份 JSON 模型，页面只是它的渲染器。**

```js
MODEL = {
  meta: { product, category, version },
  blocks: [{ id, name, note }],
  funcs:  [{ id, block, name, source, status }],
  questions: [{
    qid, kind,          // kind: plain | risk | exclude
    title, why,         // risk 必须写 why（不问会怎样）
    type,               // single | multi
    required,           // true = 未答即阻断
    options: [{ oid, label, note, conflicts: [oid], requires: [oid] }]
  }]
}
```

| 字段 | 规则 |
|---|---|
| `funcs[].id` | `B-{品类}-{板块}-{号}`，冻结不复用 |
| `funcs[].source` | `材料 / AI建议 / 主理人确认` |
| `funcs[].status` | `必做 / 二期 / 不做 / 待确认` |
| `options[].conflicts` | 填**别的题的 oid**（同题互斥由单选本身保证） |
| `options[].requires` | 选了 A 必须先选 B |
| `required` | 风险题一律 `true`；留空即阻断 |

**引擎行为（固定，不许各写各的）**：
1. 未答必答题 → 阻断；
2. 任一对 `conflicts` 同时命中 → 阻断；
3. `requires` 未满足 → 阻断；
4. `待确认`（AI 候选）默认不勾选；**勾选 = 确认采用**，来源转「主理人确认」、状态转「必做」；未勾选不进答案。
5. `二期` 默认不勾选，勾选 = 纳入本期，输出仍标「二期」（不得写成「必做」）。
6. `必做` 默认勾选，可取消；`不做` 禁选。
7. 未勾板块，其功能一律不计入答案（`validate` 阻断）。
8. 模型里查不到的 id → 阻断（**fail-closed**，不默认放行）。

**基准实现**：`模板_问卷引擎.html`（同目录）。改品类只改 `MODEL` 一段，渲染与校验不动。
**反例**：`示例\冲突阻断_演示.png`（`?demo=conflict` 打开即可复现两条阻断）。

## 十七、产品功能说明书（S1，唯一权威）

> 它定义**用户可见的行为、业务规则、验收结果**；
> 它**不定义**技术选型、存储引擎、路由、接口、表结构——那些是 AI-A 在 S5 方案里提出的。
> 一份说明书没定稿，就不许建方案任务。

### 17.1 位置

```
需求问卷 → 需求图 → 【产品功能说明书 v1.0】→ 任务书（引用）→ 效果图 → 方案
```

### 17.2 谁写、谁确认

| 角色 | 动作 |
|---|---|
| AI-C | 起草；每块标来源 ID（16.11） |
| 主理人 | 逐章确认，改动写进变更记录 |
| AI-A | **只读**；发现矛盾必须提出，不得自行解释；**不得改说明书** |

### 17.3 必含 0–10 共 11 章

| # | 章节 | 写什么 | 不许写 |
|---|---|---|---|
| 0 | 文档信息 | 版本、依据、**协作范围**（单机/多设备）、有无后端 | — |
| 1 | 概述 | 一句话、用户、三场景、不做 | 技术方案 |
| 2 | 角色与权限 | 矩阵 / 行级 / 字段级 / 越权表现 | 鉴权实现方式 |
| 3 | 板块与功能 | 每板块六格 + 功能行（带 ID） | 组件名、类名 |
| 4 | 流程运转 | 主流程 / 异常 / 状态机 | 代码流程 |
| 5 | 数据语义 | 有哪些对象、字段的业务含义、约束 | 表结构、类型、索引 |
| 6 | 前端行为 | 页面清单（业务名）、四态、断点 | 路由路径、框架、组件树 |
| 7 | 后端行为 | 若**有后端**：要提供哪些能力、权限粒度、错误提示语义；**无后端必须写明"无后端"并给数据保全规则** | 接口路径、HTTP 方法、中间件 |
| 8 | 非功能 | 引用 11 格编号（C1–C11），只写业务影响 | 重复定义数值 |
| 9 | 验收 | V1..Vn + 负向 3 项，每项对应功能 ID | 测试代码 |
| 10 | 变更记录 | 版本、改了什么、依据 | — |

**判据**：说明书里出现"接口 / 路由 / 表 / 字段类型 / 索引 / 哈希算法 / 同步机制"这类词，只能作为**外部约束**出现，并标"约束来源"（例如"受 C3 约束：只存本地"）。

### 17.4 三条硬要求

1. **能验证**：写"保存后刷新仍在"，不写"保存可靠"。
2. **标来源**：每块标 `材料 / AI建议 / 主理人确认` + 功能 ID。
3. **不写技术方案**：只写"要什么"，"怎么做"留给方案——否则门① 无从审起。

### 17.5 无后端项目的额外硬要求

无后端 ≠ 不用考虑数据安全。必须写清六条：

| # | 要求 |
|---|---|
| 1 | 每次清空 / 导入 / schema 迁移前，**自动生成带 hash 的备份** |
| 2 | 保留最近 N 份可恢复备份，界面上显示**最后备份时间** |
| 3 | 导入先完整校验 + 试运行，成功后才替换；失败**保持原数据不动** |
| 4 | 同一浏览器多标签并发：用锁或版本号，后写者失败并提示 |
| 5 | 存储配额不足时**阻止继续写入**并提示导出 |
| 6 | 验收必须覆盖：损坏备份、恢复中断、配额耗尽、双标签并发 |

### 17.6 定稿门槛（v0.x 不得进方案）

| 状态 | 能否进入 S5 方案 |
|---|---|
| `v0.x 草案`（AI-C 推导，含待确认项） | **禁止** |
| `v1.0 已定稿`（待确认清零 + 主理人逐章确认 + 状态行改为"已定稿"） | 允许 |

**规矩**：待确认项没清零，就只能在 S0–S4 里用，**不许传给 AI-A 当方案依据**；标了"候选"的建议不得写入必做功能、数据模型或验收项。

### 17.6.1 阻断级待确认项（v4.33 新增）

> 待确认项分轻重：有的不影响定稿，有的**会改变范围、工期或可行性**，后者叫"阻断级待确认"。

| 类型 | 例子 | 处理 |
|---|---|---|
| 普通待确认 | "要不要二维码扫码"（可加可减，不改变主结构） | 可留到下一版 |
| **阻断级待确认** | "硬件协议未知"、"有无后端没定"、"数据源有没有权限" | **不得标定稿** |

**判定**：一项待确认如果会导致"做出来的东西作废 / 工期无法估 / 根本做不了"，就是阻断级。

**规矩**：

1. 说明书存在**阻断级待确认项**时，**不得写 `v1.0 已定稿`**，只能标 `v0.x`；
2. 阻断级项必须写进固定章节「已知风险与待确认」，写明：`风险 / 影响 / 谁来定 / 什么时候必须定`；
3. 只有阻断级项全部清零（或降级为普通待确认），才能升 `v1.0`。

> **v4.51 口径统一（纯文档增补：不新增门禁、不改门①–⑤ 判据、不改工具行为）**
> 为什么加：把「要拍板 / 还没定」一次列清并集中落盘，省掉方案阶段反复回头问老板的时间；临时报告不进项目目录，避免被误当交付物重复核对——直接缩短需求定位时间、减少返工。
1. 决策记录的正式载体 = 说明书「已知风险与待确认」章节 + `03_模板\决策记录_模板.md`，两者同源，不另起第二套台账；
2. 状态词统一为 `已定 / 待确认`；`阻断级=是` = 会改变范围 / 工期 / 可行性，沿用上文规矩 1–3：不得标 `v1.0 已定稿`，也不得进 S4 冻结（工具接线属 v4.60，本批只写判据）；
3. 决策 ID 用 `D-{品类}-{序号}`，与 16.11 的 `B-` 功能 ID、`V-` 验收 ID 并列为第三类前缀；每行标来源与关联功能 ID，能一次追到「这条需求哪来的」；
4. 本批不新增门禁，门①–⑤ 判据不变——以上只是把 §17.6.1 既有口径写成可查的落盘位置，流程形态不变；
5. **文档级红线**：评审、扫描、对比类报告一律写系统临时目录（Windows `%TEMP%` / macOS·Linux `/tmp`），不得落到项目目录；仅交付物与冻结产物才进项目目录。

### 17.6.2 问卷答案 → 说明书 §3，别手抄（v4.40 新增）

问卷引擎的输出是**扁平一长串**，说明书的 §3 要的是**按板块分组的表格**。两者之间原来靠人搬，一个 23 功能的项目要手抄 23 行 + 补 69 格。

```bash
python 02_工具/问卷转说明书.py --q "S0.1_问卷.html" --out "§3_板块与功能.md"
```

| 它自动做 | 它还留给人 |
|---|---|
| 按板块分组（保持模型顺序） | **入口** |
| 编号去前缀（`B-YKT-CARD-01` → `CARD-01`） | **结果** |
| 补板块标题 + 板块说明 | **失败提示** |
| 待确认 / 二期 / 不做 分列清单 | |
| 状态统计（必做 N / 待确认 N …） | |

**为什么只自动这三列不自动**：分组、编号、标题是**搬运**；入口、结果、失败提示是**设计判断**——必须人（或 AI-C）真的想过"从哪儿进、点完发生什么、失败了提示什么"。自动填这三列等于编造。

产物是标准 markdown 表格，可以直接拼进说明书，也能直接喂给 `任务书生成.py` 和 `门禁矩阵.py`。

## 附录 §17.7 · 13–30 档席位号说明（v4.60 增补）

> 本节只做说明：不新增门禁、不改门①–⑤ 判据、不改工具行为。

1. 3–12 档沿用 `PLANS` 的 A1/A2/A3、I1、B1–B3、C1–C3 席位号，所属角色族为 AI-A（写码）/ AI-B（构建）/ AI-C（审核、台账）。
2. 13–30 档由 `S-1_环境初始化.html` 的自动岗位分配产生，席位号统一为 `R01–R30`，是**自动分配序号**，本身不带岗位含义；`grp` 字段仍对应 AI-A / AI-B / AI-C，与 3–12 档 A/I/B/C 同族，职责类另分写码 / 审核 / 构建 / 中立。
3. **席位号只做标识，工具不解析席位 ID**：已核对 `02_工具` 6 个 `.py` 均不解析席位 ID；`门禁矩阵.py` 中的 `V1` 是验收项编号，不是席位。
4. 席位表以「岗位｜席位名｜顶岗AI｜是否兼岗」为唯一明细来源；`角色席位：` 只给四族席数摘要，不逐 AI 重复。
5. 岗位目录以 `03_模板/岗位目录.json` 为准（4 层 23 岗，无「灵活层」）；AI 数 ≥ 23 时先给 23 岗各 1 席，剩余席位按重负载岗位拆多席；AI 数 < 23 时在「缺口 / 超载提示」列出未启用岗位清单。
