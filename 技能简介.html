为什么不能「N 个主理人」

冲突面 = n(n-1)/2。人一多，拍板就散了。

1 个主理人
0
冲突面
2 个主理人
1
对账口径对不上
3 个主理人
3
三人三答案
4 个主理人
6
共享契约互相踩

实测推演：校园一卡通

2 个主理人 → 一个要"消费实时扣款"、一个要"门禁断网也能刷" → 同一个账户两种口径，对账卡死。
3 个主理人 → "挂失后门禁要不要立刻停？" → 三人三答案，没人裁决。
换「1 主理人 + N 小组队长」 → 队长只在自己板块内确认，碰共享契约一律上报 → 冲突面归零。

一句话

打架不是因为 AI 多，是因为「没主」和「无序」。
这套流程给了：每块地有主 · 每次合并有人 · 每一步有据 · 每一门有签。

完整运作流程

从"开机四问"到"发版"，每一阶段谁做、产出什么、过哪道门。

S-1 环境初始化AI-C 引导 / 主理人答

四问：选模型（建议 PRO）· 定 AI 数量（≥3）· 按数量分配角色 · 指定项目目录

产出：00_环境.md
S0 需求主理人

说清要什么；有材料（文档/截图）先给材料，AI 复述确认后再问缺口

产出：需求原话
S0.1 需求问卷AI-C 生成 / 主理人填

按品类搜真实对标 → 拆模块 → 标必做/二期/不做 → 反推出题；生成前跑冲突校验

产出：问卷答案
S0.2 需求图AI-C

功能地图（必出）+ 主流程（有场景时）+ 角色权限（≥2 角色必出）

产出：需求图
S1 产品功能说明书AI-C 起草 / 主理人确认

11 章：概述 / 角色权限 / 板块功能 / 流程 / 数据 / 前端 / 后端 / 非功能 / 验收 / 变更

产出：说明书 v1.0（唯一权威，v0.x 禁止进方案）
S1.1 任务书AI-C

只引用说明书章节 + 本次范围 + 预览环境 + 拆分结果 + 并行度复核

产出：任务书
S2 效果图AI-A

① 先定风格（12 种选型页）② 分批出「一份 HTML 多页可切换」的可点效果图

产出：效果图
S3 看图批注主理人必选阶段

必选：必须看完效果图并给出结论（改哪、留哪、删哪）。
可选：用哪种方式给结论——
① 在调试台里双击直接改（快）　② 口头/文字批注"按钮换绿色、导航挪到左边"，由 AI-A 改

产出：修改记录 / 一句"通过"
S4 冻结AI-C

风格锁定（风格锁定：是）+ 打 stage tag + 基线提交

产出：冻结基线
S4.5 接入调度台流程主理人（调度台 DSH）

建调度台项目、填 S4 目录、加主理人/大BOSS/AI、交接 S4 产物、建 S5 门①工单草稿；不是新门禁，门①仍由大BOSS拍板。

产出：调度台项目 + S5 工单草稿
S5 方案AI-A门① 方案审

技术选型 + 六条硬要求 + 逐项落地写法（文件+行号+可粘贴）

产出：方案
S6 实施AI-A / AI-B / 独立验收人门② ③ ④

按板块竖切，一块一块做；每块一个可见里程碑；多 AI 并行时走写租约 + 集成 owner

产出：代码 + 产物
发版主理人门⑤ 终验

只认证据矩阵，缺任一验收项不签；通过后打 vX.Y.Z

产出：版本 + tag

角色边界：流程主理人 = 唯一决策席位；调度台主理人 = 该席位在调度台中的 DSH/process AI；大BOSS = 人工拍板席位，不执行 AI 工单、不代替门④独立验收人。
没有调度台时走 S4.5-Lite：复制 03_模板/S4_接入卡.md 人工交接，不阻断流程。

5

五道门守什么

每道门都要签字、留证。做的人不能给自己盖章。

门谁签判据不通过
① 方案审AI-C能落地 / 影响面说清 / 不冲突 / 回滚点齐打回重写
② 代码审AI-C只读不跑：参数没写反、边界没漏、没误改别处打回
③ 构建自检AI-B编译打包成功、版本号对、静态检查零错、命令与退出码入档退回 AI-A
④ 独立验收非构建者正向 N 项 + 负向 3 项 + 证据退回
⑤ 终验发版主理人只认证据矩阵，缺一项不签不发版

门③ 与 门④ 必须分开签：构建者只能证明"产物生成了"，不能证明"行为正确"。

6

调试台：改 UI 就等于改源码

没有"设计稿 → 写代码"的二次翻译，也没有"每个队长一套环境"的混乱。

🖥 特点一：改 UI 就是改源码

左边是真实运行的页面，右边是同一份源码。点左边元素 → 右边跳到那段代码； 双击代码行改 → Ctrl+S → 源码文件真的变了。

所以"图"和"码"不是两份东西，是同一份——物理上就不存在对不上的可能。

点元素跳代码双击即编辑改坏能撤销自动备份 30 份
维度传统做法用调试台
出的"图"设计稿（图片/原型），不能跑就是能跑的源码
改一次要几步改图 → 说明 → 开发再改码（两次）改图 = 改码（一次）
图码一致性永远对不上，靠人对齐同一份文件，无对齐成本
交付物图 + 码两份一份

🎖 特点二：不干扰多队长分工

一个项目 = 一个调试台 = 一份源码 = 一个端口。 小组队长分的是需求确认范围，不是环境副本——所以 3 个队长不会拉出 3 个版本。

① 单一入口

不管几个队长、几个 AI，大家看的是同一个页面、同一份源码

② 写租约兜底

同一文件同一时刻只有一个 owner 在改，改 UI 也受租约约束

③ 安全编辑兜底

谁改都只能改 UI 层；改逻辑一律转候选补丁，必须走任务书

结果：队长越多，分的是"管哪块需求"，不是"各改一套"—— 环境永远只有一份，所以不会打架，也不会版本分裂。

📐 特点三：网格 + 量尺，把「往右一点」变成「往右 12px」

预览区左上角两个开关，都只做叠加层，不改一行源码：

▦ 网格

细格 8px（常见间距基数）、粗格 80px（大范围定位）的虚线格。 不挡点击，不影响原有"点元素跳代码"。

⌖ 量尺

点击即钉住坐标：画红十字 + 标签，坐标冻结不动。 点第二下量出 dx / dy / 距离，点「复制」直接发给 AI。

为什么必须"点击钉住"：早期做法是鼠标移动实时刷新坐标，手一抬数字就没了，根本记不住。

没有量尺（来回试三轮）

主理人：「这个按钮往右一点」
AI：「往右多少？」
主理人：「大概 20px？」
→ 改完还是不对，再往右点…三轮还没对

有量尺（一次到位）

点住按钮 → 点「复制」→ 粘给 AI：
点A：x=112 y=64　元素 a.btn
主理人：「a.btn 父内 left=112，改到 128」
→ 一次对上

为什么报「父内 left/top」而不只是屏幕坐标：改样式改的是它相对父元素的 left/top； 只给屏幕坐标，改完数字会跟着变，越改越乱。

边界（诚实说明）

不适合

· 想"一句话生成上线"的人
· 已有成熟研发流程的大公司
· 只需要改几个字的人

它保证什么

不保证一次做对。
但保证：每次改错都能看见、能退回、能查清是谁的锅。
